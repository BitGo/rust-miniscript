## Field-by-Field Analysis

### `branch_prob: None`

**What it means:** No branching probability is tracked for this wrapper.

**Why it's correct:**

- The `r:` wrapper is a simple unary wrapper that doesn't introduce any branching logic
- No `IF`/`ELSE` constructs are involved
- It simply executes its child fragment and drops the result
- Without branching, there's no branch probability to track

**Consistency:** All unary wrappers (`a:`, `s:`, `c:`, `d:`, `v:`, `j:`, `n:`) set this to `None` for the same reason.

### `sat_cost: self.sat_cost`

**What it means:** The wrapper preserves the child's witness cost.

**Why it's correct:**

The `sat_cost` field represents "The number of bytes needed to satisfy the fragment in segwit format (total length of all witness pushes, plus their own length prefixes)" according to the code documentation.

- **What OP_DROP does:** Takes the top stack element (produced by satisfying the child) and removes it from the execution stack
- **Witness data needed:** Only what the child requires; the `r:` wrapper adds zero additional witness elements
- **Key insight:** OP_DROP operates on the execution stack during script execution, not on the witness stack. It doesn't consume or require any additional witness data beyond what the child needs.

**Cost accounting model:**

```
Satisfaction of r:X = Satisfaction of X (same witness data)
```

During satisfaction:

1. Child `X` is satisfied with witness data `W` (cost: `self.sat_cost`)
2. Child pushes result onto execution stack
3. OP_DROP removes that result
4. **Total witness cost = child's cost** (no additional witness data)

**Comparison with other wrappers:**

- `cast_verify`: Uses `self.sat_cost` (preserves child cost, same as DROP)
- `cast_dupif`: Uses `2.0 + self.sat_cost` (adds witness overhead for dissatisfaction)
- `cast_nonzero`: Uses `self.sat_cost` (operates on existing data)
- `cast_drop`: Uses `self.sat_cost` (no additional witness elements)

Both `cast_verify` and `cast_drop` use `self.sat_cost` because both OP_VERIFY and OP_DROP operate only on the execution stack and require identical witness data (whatever the child needs).

### `dissat_cost: None`

**What it means:** The wrapper cannot be dissatisfied.

**Why it's correct:**

The `r:` wrapper creates a **V-type (Verify) expression**, which by definition:

- Cannot be dissatisfied (will abort execution on failure)
- Never pushes `0` on failure
- Has no dissatisfaction path

**Specification reference:** From https://bitcoin.sipa.be/miniscript/#typing:

> "**V** = Verify: expressions which cannot be satisfied, only be validated. Their dissatisfactions are always Invalid."

**Type System Contract:**

```
Input:  B-type (Boolean) expression that pushes 1 or 0
Output: V-type (Verify) expression that succeeds or aborts
```

This B→V transformation is documented in the miniscript specification as a property of wrapper fragments that convert Boolean results into verification operations.

The script translation is semantically correct:

The `r:` wrapper transforms a B-type expression (which pushes 1 or 0) into a V-type by dropping the result, making the satisfaction implicit in execution continuation rather than explicit in a stack value.

## Interpreter Evaluation

The miniscript interpreter ([`src/interpreter/mod.rs`](src/interpreter/mod.rs)) validates satisfaction witnesses by simulating Bitcoin script execution at the miniscript level. It is used during PSBT finalization to verify that constructed witnesses correctly satisfy their scripts.

### Drop Wrapper Evaluation

**Location**: [`src/interpreter/mod.rs:664-676`](src/interpreter/mod.rs#L664-L676)

The `Terminal::Drop` wrapper is evaluated using a two-phase state machine:

```rust
Terminal::Drop(ref sub) if node_state.n_evaluated == 0 => {
    self.push_evaluation_state(node_state.node, 1, 0);
    self.push_evaluation_state(sub, 0, 0);
}
Terminal::Drop(ref _sub) if node_state.n_evaluated == 1 => {
    // OP_DROP pops the top element from the stack
    self.stack.pop();
}
```

### Evaluation Phases

#### Phase 1: `n_evaluated == 0` (Setup)

```rust
Terminal::Drop(ref sub) if node_state.n_evaluated == 0 => {
    self.push_evaluation_state(node_state.node, 1, 0);
    self.push_evaluation_state(sub, 0, 0);
}
```

1. Push the Drop node back onto the state stack with `n_evaluated = 1` (marking it for phase 2)
2. Push the child fragment onto the state stack for evaluation
3. The child will be evaluated first (stack-based evaluation order)

**Execution stack state:**

```
[Drop node (n_evaluated=1), Child node (n_evaluated=0)]
                              ^ Evaluated next
```

#### Phase 2: `n_evaluated == 1` (Stack Manipulation)

```rust
Terminal::Drop(ref _sub) if node_state.n_evaluated == 1 => {
    // OP_DROP pops the top element from the stack
    self.stack.pop();
}
```

After the child has been evaluated and pushed its result onto the stack:

1. The Drop node is popped from the state stack (with `n_evaluated = 1`)
2. Execute the OP_DROP semantics: pop the top element from the evaluation stack
3. Continue execution with an empty stack (V-type semantics)

**Evaluation stack transformation:**

```
Before Drop:  [child_result]  (1 or 0 from B-type child)
After Drop:   []              (empty, V-type semantics)
```

### Pattern Consistency

This two-phase pattern matches how other similar wrappers are implemented:

**Comparison with `Terminal::Verify`:**

```rust
Terminal::ZeroNotEqual(ref sub) | Terminal::Verify(ref sub)
    if node_state.n_evaluated == 0 =>
{
    self.push_evaluation_state(node_state.node, 1, 0);
    self.push_evaluation_state(sub, 0, 0);
}
Terminal::Verify(ref _sub) if node_state.n_evaluated == 1 => {
    match self.stack.pop() {
        Some(stack::Element::Satisfied) => (),
        Some(_) => return Some(Err(Error::VerifyFailed)),
        None => return Some(Err(Error::UnexpectedStackEnd)),
    }
}
```

Both `Verify` and `Drop`:

- Use two-phase evaluation
- Evaluate the child first
- Manipulate the stack based on the child's result
- Create V-type semantics (no dissatisfaction path)

**Key difference:**

- `Verify`: Checks that the top element is `Satisfied`, aborts if not
- `Drop`: Unconditionally pops the top element, relies on V-type wrapper semantics for verification

### Design Properties

1. **Preserves B→V transformation**: The child (B-type) pushes 1 or 0, then Drop removes it, leaving an empty stack (V-type semantics)

2. **Maintains execution continuity**: Unlike `Terminal::Verify`, which explicitly checks for satisfaction, `Terminal::Drop` relies on the fact that:

   - If the child was satisfied (pushed 1): Drop removes it, execution continues
   - If the child was dissatisfied (pushed 0): Drop removes it, but the V-type wrapper contract ensures verification failure upstream

3. **Stack hygiene**: Properly cleans up the execution stack, preventing stack underflow/overflow issues

4. **Type system compliance**: The interpreter behavior matches the type system guarantee that `r:X` produces a V-type fragment

fn test_opdrop_psbt_signing() {

## Wrapper System Context

The miniscript specification defines several wrapper types that modify the behavior of fragments (https://bitcoin.sipa.be/miniscript/#fragments):

- **`a:` (Alt)**: Transforms B to W using TOALTSTACK/FROMALTSTACK
- **`s:` (Swap)**: Transforms B to W using SWAP
- **`c:` (Check)**: Transforms K to B using CHECKSIG
- **`d:` (DupIf)**: Transforms V to B using DUP IF
- **`v:` (Verify)**: Transforms B to V using VERIFY
- **`j:` (NonZero)**: Transforms B to B using SIZE 0NOTEQUAL IF
- **`n:` (ZeroNotEqual)**: Transforms B to B using 0NOTEQUAL
- **`t:` (True)**: Transforms V to B (equivalent to `and_v(X,1)`)
- **`u:` (IfFalse)**: Transforms B to B (equivalent to `or_i(0,X)`)
- **`l:` (IfFalse2)**: Transforms B to B (equivalent to `or_i(X,0)`)

**The `r:` (Drop) wrapper** is a custom extension to this system:

- **Function**: Transforms B to V using DROP
- **Script**: `[X] OP_DROP`
- **Type transformation**: B → V
- **Use case**: Converting Boolean results to verification without VERIFY opcode

While not in the original miniscript specification, `r:` follows the same design patterns and type system rules as the canonical wrappers.

## Comparison with `cast_verify`

The `r:` (drop) and `v:` (verify) wrappers are similar but distinct:

| Aspect         | `cast_verify`   | `cast_drop`     |
| -------------- | --------------- | --------------- |
| Script         | `[T] VERIFY`    | `[T] DROP`      |
| Output type    | V               | V               |
| Dissatisfiable | No              | No              |
| Sat cost       | `self.sat_cost` | `self.sat_cost` |
| Dissat cost    | `None`          | `None`          |
| Branch prob    | `None`          | `None`          |

**Similarity:** Both `cast_verify` and `cast_drop` preserve `self.sat_cost` because both OP_VERIFY and OP_DROP:

- Operate only on the execution stack (not the witness stack)
- Require identical witness data (whatever the child fragment needs)
- Add zero additional witness elements

The only difference between them is the opcode used (`OP_VERIFY` vs `OP_DROP`).

**Specification reference:** The `v:` wrapper is documented at https://bitcoin.sipa.be/miniscript/#fragments with the property:

> "**v:**X = [X] VERIFY"
>
> Type: **V** (if X is B)

The `r:` wrapper follows an analogous pattern:

> "**r:**X = [X] DROP" (custom extension)
>
> Type: **V** (if X is B)

Both transform B-type to V-type but use different opcodes and have different optimization characteristics.
